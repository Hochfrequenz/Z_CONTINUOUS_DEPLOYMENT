# Continuous deployment into SAP via abapGit - plan overview

> **For agentic workers:** this is the map. Each numbered plan below is executed with
> superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Steps use
> checkbox (`- [ ]`) syntax.

**Spec:** `docs/superpowers/specs/2026-09-28-continuous-deployment-design.md` (v3.7, on `main`). Every design decision is there; this plan repeats none of them,
it only orders the work and says how to do it.

**Status:** plans 00, 01 and 02 are complete. Plans 03 and 04 are **outlines on purpose** (see below).
**Nothing in these plans has been executed.** The ABAP in plan 02 was written to parse and type-check
under the repository's own abaplint configuration (ABAP 7.40 SP08 floor, naming and length rules),
and its tests were traced by hand against the code. It has never run on an SAP system.

## 3. The ABAP workflow used by every plan

The rules of this repository (`CLAUDE.md`): abapGit XML is **never hand-written**, objects are created
and edited on a real system through ADT, and what is committed is what SAP serialised.

The loop for one global class with local tests (`X` stands for the class name in lower case in URIs):

| # | Do | Tool |
|---|---|---|
| L1 | Create the object once | `mcp__sap-adt__create_object` `object_type=CLAS` `name=ZCL_CDEPLOY_X` `package=Z_CONTINUOUS_DEPLOYMENT` `description=...` `transport=<request>` |
| L2 | Upload the main source (definition and implementation) | `mcp__sap-adt__set_source_from_file` `object_uri=/sap/bc/adt/oo/classes/zcl_cdeploy_x` `file_path=<work file>` `transport=<request>` |
| L3 | Upload the tests | `mcp__sap-adt__lock_object`, then (first time only) `mcp__sap-adt__create_test_include`, then `mcp__sap-adt__get_include_source` (`include=testclasses`, to obtain the ETag), then `mcp__sap-adt__set_include_source` (`include=testclasses`, `source=<file content>`, `etag=<etag>`), then `mcp__sap-adt__unlock_object` |
| L4 | Syntax check | `mcp__sap-adt__syntax_check` `object_uri=...` - expect no `E` messages |
| L5 | Activate | `mcp__sap-adt__activate_object` `object_uri=...` |
| L6 | Run the tests | `mcp__sap-adt__run_unit_tests` `object_uri=...` |
| L7 | Export what SAP serialised | `mcp__sap-adt__export_package` `package_name=Z_CONTINUOUS_DEPLOYMENT` `output_dir=<existing tmp dir>` `extract=true`; copy the changed files from its `src/` into the repository's `src/` |
| L8 | Lint locally, exactly like CI | `npm ci && npx abaplint abaplint.json` in the repository root |

Conventions that apply to every task:

* **Source files** are written to a git-ignored `work/` directory (Task 0 of plan 02 adds it to
  `.gitignore`) and named as in the plan (`work/zcl_cdeploy_version.clas.abap`,
  `work/zcl_cdeploy_version.clas.testclasses.abap`). They are the input to L2 and L3. **What is
  committed is the export of L7, never the work file**: SAP re-serialises (keyword case, the
  generated DEFINITION section), so the two differ in layout. Expect a formatting-only diff and
  commit the export.
* **The red phase is never exported or committed.** A "skeleton" (the class with every method body
  emptied) is uploaded only to see the tests fail; it would fail abaplint (`unused_variables`) and
  it is wrong code. Commit only after the green run. To make a skeleton from a finished file:
  `python tools/skeleton.py work/zcl_cdeploy_x.clas.abap > work/skeleton.abap` (Task 0 adds the
  script - four lines).
* **Transport:** ask the maintainer which workbench request to use. Pass the *request*, not the task.
  **Never release a request** without explicit permission.
* **Systems:** develop and run tests on the older system first (the language floor is ABAP 7.40
  SP08; a class that activates there is safe everywhere), then pull the merged result into the newer
  system with abapGit and compare the test counts (plan 02, Task 9). Do not name systems, hosts or
  clients in commits, PRs or documents: this repository is public.
* **Review:** every task ends with the repository's rules: squash merge only, and an agent runs at
  least one round with a *separate* review agent before a PR is marked ready. A green ABAP Unit run
  on the developer's own session is not a review.
* **Naming and length limits** are enforced by `abaplint.json` (`object_naming`, the 30-character
  identifier rule). A too-long test method name is the most common failure; keep them short.

## 4. Findings made while writing these plans (fold back into the spec)

None of these blocks the plans; each should be reflected in the spec in a small follow-up PR.

1. **A failing snapshot is reported as a poll error of class `CONFIG`**, not as an attempt failure
   (`DEPLOY_ERROR`), as spec 3.1 and 6.1 say. Reason: the snapshot is taken *before* the attempt
   marker, so nothing has been counted or started; treating it as an attempt would either need a
   marker without a baseline or count an attempt that never began. It is retried next minute.
2. **Two interfaces the spec does not list are needed as test seams:** `ZIF_CDEPLOY_CLOCK` (the only
   place the clock is read) and the lock/commit methods on `ZIF_CDEPLOY_STATE`. `COMMIT WORK` and
   the enqueue therefore live behind the state interface.
3. **The status light needs no configuration table.** Spec 6.6 says "state table and configuration
   table"; the predicates as written use only the state row (a capped tag is `FAIL_TAG` with an
   `ATTEMPT_ERROR`).
4. **abaplint needs `dependencies`** to know any standard SAP class (`CX_STATIC_CHECK` and friends);
   without them the first exception class fails `check_syntax`. Fixed in PR #3.
5. **The language floor is enforced by the linter, and it bites:** `RAISE EXCEPTION NEW ...` is ABAP
   7.52 syntax and is rejected at 7.40 SP08; `TYPE c LENGTH n` is not allowed in a method signature
   (use a named type). Write `RAISE EXCEPTION TYPE ... EXPORTING ...`.
6. **Log entries exist only for alerting failures and real events.** Quiet outcomes
   (`NOTHING_TO_DO`, `SKIPPED`, a non-alerting repeat) write nothing to the log, as spec 6.4 says;
   the orchestrator implements exactly that.

## 6. Outline of plan 04 (reporter and reports)

`ZCL_CDEPLOY_REPORTER_GITHUB` / `_NULL` (spike 9.11), the batch report `Z_CONTINUOUS_DEPLOYMENT`
(dry-run parameter, final `E` message when `error_exit` is set), `Z_CONTINUOUS_DEPLOYMENT_SETUP`
(store/rotate/delete a PAT; `RESET_ATTEMPTS`, `CLEAR_SNAPSHOT`, `RESET_DEPLOYED`),
`Z_CONTINUOUS_DEPLOYMENT_STATUS` (ALV over `ZCL_CDEPLOY_STATUS_LIGHT`), the README, and the batch-job
scheduling instructions (every minute).
