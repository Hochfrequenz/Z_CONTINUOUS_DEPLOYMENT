# Spike - answer the open questions of spec section 9 - plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development (recommended)
> or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** turn every "read in source, never run" claim of spec section 8 and every open item of
section 9 into a recorded, dated result, so that plan 03 is written against facts.

**Architecture:** one throwaway ABAP class per question, run with `mcp__sap-adt__run_class`
(`IF_OO_ADT_CLASSRUN`), writing its findings to the console. The probes live in `$TMP`; nothing is
transported. Findings go into `docs/spike/RESULTS.md` in generic terms.

**Tech stack:** ABAP on the older and the newer system, abapGit developer edition (global
`ZCL_ABAPGIT_*` classes), one GitHub fixture repository, two fine-grained PATs.

**Spec:** `docs/superpowers/specs/2026-09-28-continuous-deployment-design.md`, sections 8 and 9.

---

## Ground rules

* **The systems are test systems, but the fixtures still must not touch real work.** Use only the
  fixture repository and the throwaway package below. Do not pull anything into a package that holds
  real objects.
* **Read-only first.** Tasks S1 to S6 and S10 to S12 create only fixture objects. Task S9 takes an
  enqueue lock on a fixture key. No probe writes to a productive table.
* **Do not put system names, hosts, clients, user names or tokens in `RESULTS.md`, in commits or in
  PRs.** Say "the older system" and "the newer system". Never paste a PAT anywhere.
* **A result is a fact, not a guess:** each task ends with the exact observation, the date, the two
  systems' abapGit source dates, and a one-line consequence for the spec.
* **Confirm every abapGit signature by reading it first.** The probes below use only calls that
  were read in source (spec section 8). Anything marked *confirm* must be read with
  `mcp__sap-adt__get_source` or `get_class_definition` before it is called, and the confirmed
  signature written into `RESULTS.md`.

## S1 (9.1) Pull a tag through `select_branch` + `deserialize`, in a batch context

**Question:** does `select_branch( 'refs/tags/v0.1.0' )` followed by `deserialize_checks( )` and
`deserialize( )` deserialise the tag's content, in a job with no dialog, for a public repository?
Does `refs/tags/*` behave as a tag at runtime?

* [ ] Read `ZIF_ABAPGIT_REPO_SRV` (`get_source`) and write down how to obtain a repository object by
  key (*confirm*: expected `zcl_abapgit_repo_srv=>get_instance( )->get( iv_key )`).
* [ ] Create `ZCL_CDEPLOY_SPIKE_1` in `$TMP` implementing `IF_OO_ADT_CLASSRUN`. Skeleton (fill the
  *confirm* parts after reading):

```abap
CLASS zcl_cdeploy_spike_1 DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    INTERFACES if_oo_adt_classrun.
ENDCLASS.

CLASS zcl_cdeploy_spike_1 IMPLEMENTATION.
  METHOD if_oo_adt_classrun~main.
    " KEY = the abapGit key of the fixture on THIS system (12 characters)
    CONSTANTS lc_key TYPE zif_abapgit_persistence=>ty_value VALUE '<KEY>'.
    TRY.
        " confirm: how to get the repository object for lc_key
        DATA(li_repo) = zcl_abapgit_repo_srv=>get_instance( )->get( lc_key ).
        DATA(lo_online) = CAST zcl_abapgit_repo_online( li_repo ).

        out->write( |selected before: { lo_online->get_selected_branch( ) }| ).
        lo_online->select_branch( 'refs/tags/v0.1.0' ).
        out->write( |selected after:  { lo_online->get_selected_branch( ) }| ).
        out->write( |remote commit:   { lo_online->get_current_remote( ) }| ).

        DATA(ls_checks) = li_repo->deserialize_checks( ).
        " confirm: the structure zif_abapgit_definitions=>ty_deserialize_checks - dump it
        out->write( data = ls_checks name = 'CHECKS' ).

        " confirm: which class implements zif_abapgit_log (zcl_abapgit_log)
        DATA(li_log) = CAST zif_abapgit_log( NEW zcl_abapgit_log( ) ).
        DATA(lv_before) = li_repo->ms_data-deserialized_at.
        li_repo->deserialize( is_checks = ls_checks ii_log = li_log ).
        out->write( |deserialized_at: { lv_before } -> { li_repo->ms_data-deserialized_at }| ).
      CATCH cx_root INTO DATA(lx).
        out->write( |EXCEPTION { cl_abap_classdescr=>describe_by_object_ref( lx )->get_relative_name( ) }: { lx->get_text( ) }| ).
    ENDTRY.
  ENDMETHOD.
ENDCLASS.
```

* [ ] Activate; run with `mcp__sap-adt__run_class`. Run it again as a **background job** (SM36 /
  `sap_transaction`), because a dialog-only success proves nothing: repeat and compare the output.
* [ ] **Record:** the final selected branch, that class A of `v0.1.0` now exists, whether the job
  needed any dialog answer, every `deserialize_checks` field that was not initial.
* **Decision rule:** pass = the objects of the tag exist and no dialog was raised. Fail = an unhandled
  exception or a popup: record it; plan 03's deployer needs a different entry point.

## S2 (9.2) How annotated tags come out of `get_tags_only`

* [ ] Class `ZCL_CDEPLOY_SPIKE_2`: call
  `zcl_abapgit_git_factory=>get_git_transport( )->branches( iv_url )->get_tags_only( )` for the
  public fixture URL and dump the table (`out->write( data = ... )`).
* [ ] **Record:** for `v0.2.0` (annotated) and `v0.1.0` (lightweight), the `name`, `sha1` and any
  peeled entry (`^{}`) in the result; which of the two SHAs is the commit (compare with
  `get_current_remote( )` after S1 for `v0.2.0`).
* **Decision rule:** the adapter must return the **commit** per tag. If the table gives the tag-object
  SHA for annotated tags and a peeled entry separately, the adapter joins them; if it gives no peeled
  entry, the commit has to be obtained another way (record how).

## S3 (9.3) Which API says "the remote differs from the local objects"

* [ ] Read `ZCL_ABAPGIT_REPO_STATUS` (`get_class_definition`); *confirm* a method that returns
  per-object status for a repository (expected `calculate( io_repo )`).
* [ ] Class `ZCL_CDEPLOY_SPIKE_3`: after S1 (repository at `v0.1.0`), call it for the repository at
  `v0.1.0` (up to date) and after `select_branch( 'refs/tags/v0.2.0' )` (class A differs). Dump both.
* **Record:** what the result table looks like in each case, and the exact test for "nothing to
  deserialise" (spec 5.2).
* **Decision rule:** an empty result table (or no entry with a difference) for the up-to-date case and
  a non-empty one for the differing case. If not distinguishable, the clean-slate shortcut is dropped
  and every attempt pulls (a spec 5.2 change).

## S4 (9.4) Does `deserialized_at` move on a pull that changes nothing?  **(gate G2)**

* [ ] Class `ZCL_CDEPLOY_SPIKE_4`: at `v0.2.0` (deployed), read `ms_data-deserialized_at`, switch to
  `v0.3.0` (**identical content**), pull, read it again; then pull `v0.3.0` a **second** time and read
  it once more. Also do the same with `v0.4.0` (real change).
* **Record:** the three timestamps as before/after pairs: pull with changes, pull with identical
  content, second pull of the same tag.
* **Decision rule:** if an empty pull does **not** move the timestamp, check 1 would fail a legitimate
  retry of a complete tag forever; the spec already treats that as a safe failure with operator
  recovery (6.5) - record it and stop. If it **always** moves, note that `NO_CHANGE` can only come from
  the status shortcut (S3).

## S5 (9.5) Exception or log?

* [ ] Class `ZCL_CDEPLOY_SPIKE_5`: pull `v0.4.0` (class B does not activate). Catch `cx_root`, and also
  read the log (`li_log`) afterwards. Dump both.
* **Record:** for each kind of failure (syntax error, missing package, locked object if reproducible,
  authorisation) whether abapGit raised an exception or only put a message into the log, and the
  method that lists per-object messages from the log (*confirm* on `ZIF_ABAPGIT_LOG`).
* **Decision rule:** `ZCL_CDEPLOY_CHECKS` check 3 is fed from whichever of the two holds the errors; the
  adapter must read **both**. Record the mapping.

## S6 (9.6) What `deserialize_checks` says in a batch, and how much SAP-generated drift there is

* [ ] Class `ZCL_CDEPLOY_SPIKE_6`: pull `v0.2.0`, then call `deserialize_checks( )` for the **same
  tag** a second time and dump `overwrite`, `warning_package`, `requirements`, `transport` and any
  other non-initial field.
* [ ] Change class A on the system with the ADT tools (as a different "user" if possible) and dump
  again.
* **Record:** (a) the fields that can require an answer in an unattended run and how to detect
  "decisions missing"; (b) **how many objects appear as "changed locally" right after a clean pull with
  nobody having touched them** (SAP-generated drift; this decides whether `OVERWRITE_POLICY` `NEVER`
  is usable at all); (c) whether a per-object "changed by" is present and reliable for the object
  types in use (this decides whether `BLOCK_FOREIGN` ships).
* **Decision rule:** if (c) is missing for common types, drop `BLOCK_FOREIGN` from v1 (spec 5.2 says
  nothing else changes).

## S7 (9.7) Is a switch to a tag honoured on a repository object built earlier in the same process?

* [ ] Class `ZCL_CDEPLOY_SPIKE_7`: get the repository object once, `select_branch( v0.1.0 )`, deserialise;
  in the **same session** without re-reading the repository call `select_branch( v0.2.0 )` and
  deserialise again. Also try `zcl_abapgit_repo_srv=>get_instance( )->refresh( )` between them if it
  exists (*confirm*).
* **Record:** whether the second deserialisation used `v0.2.0` or still `v0.1.0`, and the sequence that
  is reliable. This decides whether the orchestrator must re-read the repository object per attempt.

## S8 (9.8) Is `SECSTORE_*` released for customer use?

* [ ] Look up the release/API state of `SECSTORE_INSERT_ITEM`, `SECSTORE_READ_ITEM` and

## S9 (9.9) Does anything in a pull release the scope-1 lock?  **(gate G1)**

* [ ] Class `ZCL_CDEPLOY_SPIKE_9`: enqueue an existing lock object (any standard one, on a dummy key -
  `ENQUEUE_E_TABLE` on a fixture table name) with `_scope = '1'`, `_wait = space`; confirm it with
  `ENQUEUE_READ`; run the full S1 pull of `v0.4.0` **including a failing activation**; call
  `ENQUEUE_READ` again; try to enqueue the same key from a second session
  (`mcp__sap-adt__run_class` in parallel, or a background job) during and after.
* **Record:** whether the lock was still held after each `COMMIT WORK` inside the pull, after a
  failing activation, and after an exception; and the second session's result.
* **Decision rule (gate G1):** lock survives -> keep the one-minute period. Lock dropped -> spec 6.3's
  fallbacks apply: (a) a guard refusing to start while an earlier instance of the job is still active
  in the job tables, or (b) a period longer than the longest pull. Decide with the maintainer before
  plan 03.

## S10 (9.10) Is a PAT accepted as a basic-authentication password on GitHub?

* [ ] Class `ZCL_CDEPLOY_SPIKE_10`: read the PAT from the secure store (S8), then

* **Record:** works with the PAT and the fixed user name `token`: yes/no; the failure without it

## S11 (9.11) Can the Deployments API be called from ABAP?

* [ ] Class `ZCL_CDEPLOY_SPIKE_11`: with `pat_deploy`, through the same proxy and certificate setup as
  the git requests, call in order: `GET /repos/{owner}/{repo}` (read `private`), `POST
  /repos/{owner}/{repo}/deployments` (`ref` = a tag, `auto_merge=false`, `required_contexts=[]`,
  `production_environment=false`, `environment` = an alias), `POST .../deployments/{id}/statuses`
  (`in_progress`, then `success`), `GET .../deployments?environment=...`. Use a 5-second timeout on each.
  Use `cl_http_client=>create_by_url` (or abapGit's `zcl_abapgit_http_client`) - *confirm* which is
  usable on both systems.
* **Record:** which call needed which PAT permission; whether visibility can be read with the same PAT;
  the time each call took; whether a call on a stale/unknown PAT fails cleanly with a status code.
* **Decision rule:** any call that cannot be made -> reporting stays off on that system and the spec
  says so.

## S12 (9.12) What does a poll cost?

* [ ] Class `ZCL_CDEPLOY_SPIKE_12`: time 20 consecutive `get_tags_only` calls on the public fixture and on
  a large public repository; record the payload size if available.
* **Record:** median and worst time, and whether the ref advertisement includes `refs/pull/*` and how
  large it is (GitHub lists every ref). Note whether abapGit's transport can restrict it.
* **Decision rule:** median under two seconds -> one-minute period is cheap. Otherwise say what dominates.
